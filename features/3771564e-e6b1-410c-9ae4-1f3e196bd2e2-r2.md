## 2. Root cause & decisions

ROOT_CAUSE (round 3, follow-up to c70a7db/dec6f03 = round 1/2, merged dev@5acfccd82a23):
round 2 fixed `Indexer.scan()`'s directory-walk cost (the `.worktrees` mismatch +
`rglob`-has-no-pruning-hook bug) but left the actual write-blocking symptom only
half-fixed. `REINDEX_COMMIT_BATCH` (the periodic commit inside `reindex()`) is a
CHANGE-count threshold — `since_commit` only increments on a real add/update, so a
run with few real changes relative to many unchanged docs never reaches it. Live
post-deploy prod evidence (rowid #468 in `index_runs`, captured via cto-tsukumo):
25 added vs 11160 unchanged in one cycle — `since_commit` maxes out around 25,
never gets near 200, so the ENTIRE reindex (200-600+ seconds, confirmed via
`index_runs.duration_sec` on prior cycles) commits exactly ONCE, at the very end.

Independently reproduced live: with ONLY the server's own single in-progress
reindex process running (verified via `lsof`/`ps` — no competing writer, ruled out
by both cto-tsukumo and myself), `trovex_write` still timed out at 30s. This
confirms the mechanism: the long-open transaction on `indexer.db` blocks
`store.db`'s writes via SQLite's single-writer-per-file semantics, independent of
the `.worktrees` fix (which only reduced how long the SCAN portion itself takes,
not how often the transaction commits).

Ruled out as the cause (verified, not assumed): the scan/walk itself is fast
post-round-2 — measured directly against the live prod sources (trovex-repo,
tsukumo, wraith, niwa-lessons): raw `_walk_files` walk = ~4629 files in 28ms;
full `scan()` incl. `_accept()` filtering = ~1507 indexable files in ~70ms. The
200-600s duration is NOT the file-scan/walk; it's the DB-side per-doc work
(mtime-fast-path stat/hash checks across ~11k+ tracked docs, and separately
compute_status's own per-doc file reads/KNN — the latter is real but ALREADY
correctly batched via its own periodic commits, see `status.py` Pass 1/Pass 2,
and is a separate, non-blocking concern noted as a follow-up, not part of this fix).

DECISION: add `REINDEX_COMMIT_INTERVAL_SEC` (1.0s) — a time-based flush checked
on EVERY scanned path (not only ones that write), so it also fires while walking
a long run of unchanged docs between real changes, regardless of the
change/unchanged ratio. Applied to both the main scan loop AND the removal loop
(`delete_doc_cascade` calls), which had ZERO batching before (a large single-run
removal count, e.g. an already-observed removed=357 in one historical
`index_runs` row, would hit the exact same class of bug). Also fixed: the
"content identical, mtime moved" refresh-only `UPDATE` branch is a real write
that wasn't counted toward `since_commit` at all — a run dominated by that branch
could still skip flushing.

Both triggers (count ≥200 OR elapsed ≥1s) OR together; whichever fires first
flushes. The time-check sits at the TOP of each loop iteration (before any
per-doc work), so it never splits a single doc's multi-statement write mid-flight
— preserves the existing "each doc's write is already atomic" invariant the
count-based design documents.

EVIDENCE: new test `test_concurrent_write_stays_fast_during_low_change_ratio_scan`
(tests/test_reindex_single_flight.py) — 40 docs, 20 real changes (well under
REINDEX_COMMIT_BATCH=200, so the count-based path provably cannot fire alone),
slowed `Indexer._accept()` (called for every scanned path) so the scan is
measurably slow (~2s+ total); asserts a concurrent `SqliteStore.put()` on a
separate connection completes in well under 1s instead of waiting out the whole
scan. Negative control: fails on unpatched code (`REINDEX_COMMIT_INTERVAL_SEC`
doesn't exist pre-fix — the test hard-depends on the fix, not a coincidence).
471/471 full suite passes, ruff clean.

REJECTED_ALTERNATIVES:
- Restructure to compute scan/hash/embed entirely OUTSIDE any open transaction,
  opening one only for the final write per doc — a larger, riskier refactor for
  a P1 follow-up when a bounded flush interval directly closes the observed gap
  with a small, easily-reviewed diff. Left as a [LEGACY_OPPORTUNITY] if the
  1s-bounded hold is ever found insufficient under heavier concurrent load.
- Raise REINDEX_COMMIT_BATCH's effective reach by counting unchanged docs too
  (a count-based fix instead of time-based) — rejected because per-doc cost
  varies (a fast stat-only unchanged check vs. a slow read+hash+embed for a
  real change), so a COUNT threshold can't bound WALL-CLOCK hold time the way
  elapsed time directly does; time-based is the correct primitive for "don't
  hold the lock too long," which is the actual invariant this bug violated.
