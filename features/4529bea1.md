## 2. Root cause & decisions

# Retrieval micro-opts T3–T6 (task 4529bea1) + content_hash leak fold

ROOT_CAUSE: per-query retrieval carried avoidable cost — a rerank that re-read
~20 files off disk per query and ran even when there was nothing to reorder, a
chunk-retrieval loop that issued one SQL round-trip per candidate (N+1), and a
query cache whose single GLOBAL version string was bumped by ANY write, voiding
every cached entry fleet-wide on each trovex_write.

## CHANGES
- **T3 — already done by P2a (noted, not re-implemented).** P2a retired the
  widen-retry / 2×-KNN entirely (partitioned vec0, tiny bounded k). No rescan
  remains; only a stale "widen-retried" comment, now corrected.
- **T4 — rerank.** (a) `maybe_rerank` SKIPS when `len(candidates) <= limit` — with
  ≤limit candidates every one is returned anyway, so the O(candidates) cross-
  encoder pass can't change the result set. (b) The reranker is fed each
  candidate's body from the DB via a single batched query (first chunk per doc)
  through a `text_fn`, instead of `Path.read_text` per candidate — owned docs have
  no file at all, so the disk read returned nothing for them.
- **T5 — query cache** (`cache.py`). `corpus_version(db, scope)` is now PER-SCOPE:
  a source id's version reflects only that source's docs, so a write to another
  source no longer invalidates this scope's entries (`scope=None`, the source='*'
  query, keeps the global version). Added a TTL (`created_at` window, default 1h)
  and a row cap (default 2000, evict oldest) — both env-tunable. Never serves
  stale: a same-source write still bumps the version.
- **T6 — /search N+1** (`store.py::search_chunks`). The `for cid in ranked` loop
  did one `SELECT … WHERE c.id = ?` per candidate PLUS a per-hit tag SELECT.
  Replaced with ONE batched chunk+doc fetch (`WHERE c.id IN (…)`, chunked under
  sqlite's variable cap) and ONE batched tag fetch. Output shape unchanged.

## FOLDED (review-6c02c654, cto-approved)
The store-only vector purge cleared vectors but left `docs.content_hash` intact,
so a later identical-content flip BACK to a searchable kind hit the
content_unchanged fast-path and never re-embedded (permanent BM25-only). Both
purge branches now clear content_hash so a flip-back re-embeds.

- `test_query_cache_is_per_scope_and_ttl`: a cross-source write does NOT void a

- `test_store_only_flip_back_re_embeds`: flip to store-only then back → vectors

  cited rather than a misleading ms number.
