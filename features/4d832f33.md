## 2. Root cause & decisions

## review-trovex verdict: SHIP

ROOT_CAUSE: The corpus crossed sqlite-vec's HARD 4096 KNN ceiling. vec0 raises
OperationalError("k value in knn query too large") for any MATCH with k > 4096.
Searcher._vector_rows' widen-retry (search.py:219) set k = min(total,
MAX_KNN_POOL=20000); once the store held >4096 docs, an owner-scoped boot query
came back short on the first pass (k before the lifecycle/scope filter), fired
the widen-retry with k = total (>4096), and threw. boot_pointers did not catch
it, so /api/boot 500'd for EVERY agent (544 knn-errors + 398 boot-500 in
serve.log) — the whole fleet's Active-Memory boot was down.

DECISION (defence in depth, ~3 lines of real fix + 2 defensive clamps):
1. search.py — add SQLITE_VEC_MAX_K=4096; clamp the widen-retry k to
   min(total, MAX_KNN_POOL, SQLITE_VEC_MAX_K); defensively clamp the initial
   pool to the ceiling too. The widen scan is capped at 4096, not the doc count.
   (Consequence: on a >4096-doc store the widen-retry scans the 4096 nearest,
   not the whole index — sqlite-vec's own limit; the archived-heavy squeeze tail
   past rank 4096 is unrecoverable by KNN, an acceptable ceiling vs a 500.)
2. store.py — clamp the chunk-search pool to 4096 (a large caller `limit` could
   push limit*6 over it).
3. boot.py — boot_pointers wraps the search in try/except sqlite3.OperationalError
   and returns an empty pointer pack; boot is best-effort and must NEVER 500.

VERIFICATION: two regression tests, both NON-VACUOUS — each first proves the
corpus genuinely exceeds the ceiling (a raw k=count MATCH still raises
OperationalError), so a regression that drops the clamp fails outright:
- tests/test_active_memory: seed >4096 docs; boot_pointers + Searcher.search
  return normally.
- tests/test_server: same at the HTTP surface — GET /api/boot and /api/search
  both return 200.
Full gate green: ruff check src tests, pytest -q -> 346 passed, brand guard clean.
