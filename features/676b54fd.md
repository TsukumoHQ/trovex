## 2. Root cause & decisions

# P3-headroom — capacity observability + usearch escape-hatch seam (task 676b54fd)

ROOT_CAUSE: the partitioned vec0 store is brute-force KNN. P2a/P2c bound each
partition, but nothing WATCHED the headroom, so a partition approaching the
brute-force ceiling would only surface as latency (or, at the hard 4096 vec0 `k`
ceiling, the P0 outage class). No observability, no documented upgrade path.

## DELIVERED
- **AC1 — capacity observability (`capacity.py`).** `partition_counts(db)` reads
  the vec0 tables (the actual KNN working set — a store-only doc has no vector and
  correctly doesn't count). `capacity_report(db)` returns partitions at/near a
  limit (owned chunks nearing the 4096 vec0 `k` ceiling, or a file source nearing
  the 100k brute-force soft limit), silent when there's headroom.
  `log_capacity_warnings(db)` emits a WARN per near-capacity partition; wired into
  `indexer.reindex` (returns `capacity_warnings` count). Observability only — zero
  behavior change.
- **AC2 — usearch escape hatch (seam + docs + flag).** `Settings.usearch_partitions`
  (env TROVEX_USEARCH_PARTITIONS, default empty) is the per-partition opt-in;
  `capacity.py`'s module docstring documents the full upgrade path (single-header
  C++ HNSW, `pip install usearch`, offline, per-partition — sqlite-vec stays
  default elsewhere). The seam + flag + the capacity trigger that PROMPTS the swap
  are wired; the default path is unchanged and offline-first.

## DEFERRED — premise drift (flagged to cto)
- **AC2 usearch BACKEND adapter — deferred as premature.** The AC assumes a
  partition near ~1e5 vectors. Post-P2a/P2c the largest real partition is tsukumo
  at ~3065 chunks — an order of magnitude under the 4096 ceiling and ~30× under
  the 100k soft limit. Building an inert HNSW query path now (it changes nothing
  until a partition crosses the threshold, which no partition is near) is
  speculative complexity + a new dependency for a day that isn't close. The seam +
  `capacity_report` are exactly what will tell us WHEN to build it.
- **AC3 MinHash/LSH ingest dedup — deferred as premise-drifted.** The AC states
  the dedup is "O(N) pairwise-cosine (status.py k=3)". It is NOT: `detect_duplicate_for`
  is already a `k=20` vec0 KNN (log-ish per doc), and the batch pass is a KNN per
  doc, not an N² pairwise scan. A MinHash/LSH layer would be a DIFFERENT (lexical)
  candidate signal, additive — a real option, but not a fix for a bottleneck that
  isn't there at current scale, and it risks perturbing the just-hardened dedup
  behavior. Recommend it stay a documented future option, revisited if
  `capacity_report` ever fires.
