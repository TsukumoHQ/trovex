## 2. Root cause & decisions

# T1 — query-embed off the loop + LRU cache (task 6c02c654) + P2c leak fold

ROOT_CAUSE: query embedding dominated search latency (measured p50 334ms / p90
977ms / p99 2154ms, n=493). Two causes: (1) the synchronous ONNX embed ran ON
the asyncio event loop inside the `async def` /api/search + /api/boot handlers, so
concurrent requests serialized head-of-line; (2) the same query embedded every
time — /api/boot re-embeds the SAME BOOT_QUERY every session, agents repeat
queries — with no cache in front of the ONNX call.

## FIX
1. **LRU query-embed cache** (`query_cache.py`): `embed_query_blob(embedder, text)`
   caches the serialized query vector by (model, text), bounded LRU (1024),
   thread-safe (embed runs outside the lock). Wired into the two query embed
   sites — `search.py::_vector_rows` and `store.py::search_chunks`. Deterministic
   per model → no correctness change, just a cache before the ONNX call. Boot's
   fixed BOOT_QUERY is a permanent hit.
2. **Off the event loop**: /api/search + /api/boot now run the sync search in
   `starlette.concurrency.run_in_threadpool`, so the ONNX embed (on a miss) + the
   sqlite KNN don't block the loop and concurrent requests don't serialize. Safe:
   the sqlite conn is `check_same_thread=False` and writes are single-writer
   locked, so a cross-thread read is fine.

## FOLDED (review-af03da67 leak, cto-approved fast-follow, batched redeploy)
P2c's `content_unchanged` fast-path returned before the store-only vector purge,
so re-putting an identical doc flipped to a store-only kind kept its vectors in
the KNN. Fixed: the fast-path now purges vec_docs/vec_chunks when the kind is
store-only. (Default-off feature; no live impact, but restores the zero-KNN
guarantee.)
