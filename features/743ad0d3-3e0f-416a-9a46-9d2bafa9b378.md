## 2. Root cause & decisions

ROOT_CAUSE: `_migrate_embed_dim` and `_migrate_partition_vec` (src/trovex/db.py) each run their DROP TABLE vec_docs (+ siblings) as separate autocommitting statements, not wrapped in one transaction with the later CREATE/reinsert. A process killed partway through (crash, kickstart restart, machine sleep) can leave vec_docs dropped while vec_chunks survives at its old schema (or vice versa) -- and each function's own early-return guard ("if not row: return") then treats a missing vec_docs as "already migrated / nothing to do" forever, permanently wedging trovex_write on "no such table: vec_docs" with no self-heal (found live on the deployed local store, task 743ad0d3).

DECISION: wrap each migration's destructive DROP+CREATE(+reinsert) sequence in one explicit BEGIN IMMEDIATE transaction with rollback-on-exception, so an interruption always leaves the OLD tables fully intact for a clean retry next boot instead of a half-migrated, unrecoverable state.

ROUND_2_FIX (reviewer-caught): `_migrate_partition_vec`'s recreate step used `conn.executescript()` for the two `CREATE VIRTUAL TABLE` statements. Python's `sqlite3.Connection.executescript()` implicitly COMMITs any pending transaction before running the script -- so it committed the preceding DROPs before either CREATE ran, breaking the exact atomicity this BEGIN IMMEDIATE exists for (a kill between that implicit commit and the CREATEs completing left both vec tables dropped-and-committed). Fixed by replacing the executescript() call with two plain `conn.execute()` calls, which participate in the already-open transaction instead of force-committing it. The original regression test armed its boom before the implicit commit point (on a `_BoomOnScript.executescript` wrapper), so it never exercised the bug -- false confidence. Replaced with `_boom_execute_conn` armed on `"CREATE VIRTUAL TABLE vec_docs"`, which fires after the DROPs and reproduces the real interrupted-recreate scenario.

REJECTED_ALTERNATIVE: adding a runtime self-heal/retry check on every write call (re-verify vec_docs exists before each trovex_write) -- treats the symptom on the hot path instead of the actual defect (non-atomic migration), adds per-write overhead, and doesn't help boot-time recall paths that hit the same missing table.

VERIFICATION: confirmed live via direct sqlite3 query against the deployed ~/.trovex-data/trovex.db -- vec_docs and its shadow tables completely absent from sqlite_master while vec_chunks was fully present/partitioned, exactly the half-migrated shape this bug produces. Immediate remediation: `launchctl kickstart -k gui/$(id -u)/com.tsukumo.trovex-serve` -- a fresh open_db()'s _init_schema (CREATE TABLE IF NOT EXISTS) recreated vec_docs instantly. Verified with a real trovex_write + trovex_read read-back over the live MCP endpoint (write succeeded, read returned the exact content, probe doc then deleted). Code fix verified with 2 new regression tests that simulate a real interruption (sqlite3.Connection subclass raising mid-execute for each migration function, armed AFTER the DROPs so it exercises the real interrupted-recreate window) and assert both (a) the old schema survives untouched by the aborted attempt and (b) a clean retry afterward self-heals fully. make test: 395 passed, ruff clean.
