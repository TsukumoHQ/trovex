## 2. Root cause & decisions

# feat/incr-reindex — content-addressed (Merkle) incremental re-embedding

Task 9d03f31d — trovex steal #2 from study 37fa8519 (Claude Context + Code
Context Engine). Keep the SSOT cheap as it grows.

ROOT_CAUSE: the file-index path already skips unchanged DOCS (mtime + content
hash), but the trovex_write / store.put path did the opposite — every overwrite
of an owned doc unconditionally re-embedded the whole doc, deleted+re-embedded
ALL of its chunks, and snapshotted a version, even when the content was
byte-identical or only one section changed. As the canon grows, a small edit
costs a full-doc re-embed (O(all chunks)) and a no-op save pollutes version
history. Chunks had no content hash, so there was no way to tell which chunk
actually changed.

## Decision (additive, correctness-critical)

Schema: `chunks.content_hash TEXT NOT NULL DEFAULT ''` + idx_chunks_hash.
Migration `_migrate_add_chunk_hash` (idempotent ALTER, legacy rows '' = not
reusable, so the first rewrite re-embeds + stamps them — same degrade model as
docs.content_hash '').

1. **Chunk-level, content-addressed reuse** (`_insert_chunks`): each new chunk is
   keyed by sha256(embed_text) = sha256(title + heading + text) — everything that
   feeds the embedding. A new chunk whose hash already exists among the doc's
   current chunks reuses that row + its vec_chunks embedding + its FTS unchanged
   (only chunk_index is refreshed); new/changed chunks are inserted + embedded;
   chunks whose hash is gone are deleted (row + vec + fts). So an edit to one
   section re-embeds ONE chunk, and a reorder re-embeds ZERO (matched by hash,
   not position). Returns only the pairs that need embedding.
2. **Doc-level no-op skip** (`store.put`): a byte-identical overwrite skips the
   version snapshot, the doc re-embed, the re-chunk, and dup-detection; only the
   cheap metadata (title/kind/tags/mtime) is refreshed, so a tag-only update
   still lands. docs.content_hash is now populated for owned docs (was '').
3. **put_batch** populates content_hash too, so imported docs are skip-eligible.

## Correctness rail

The hash covers the FULL embedding input (title+heading+text), so any genuine
change to a chunk's text, its heading, or the doc title changes its hash and
forces a re-embed — a stale embedding is never served for changed content. A
title change re-embeds all chunks (correct: title is part of embed_text).
Verified by test: changed chunk is searchable by its new text; unchanged chunk
keeps its id; removed section's embedding is deleted (no orphan/leak).

## Rejected alternatives

- **Index-position match** (reuse chunk at index i if its hash matches) —
  rejected. Inserting a paragraph at the top shifts every index → full re-embed.
  Content-addressed (hash-keyed) match survives reorders/insertions, which is the
  actual Merkle property the task asks for.
- **Skip metadata too on a no-op write** — rejected. A same-content, different-tags
  write must still update tags; only the expensive/snapshot work is skipped.
